# Inner Source 도입 로드맵

> 관련: 이슈 #43
> 작성일: 2026-11-14

**Inner Source**는 오픈소스의 협업 방식(공개 저장소, 이슈, PR, 코드 리뷰)을 **조직 내부**에 적용하는 것입니다. 코드는 조직 밖으로 공개하지 않지만, 조직 안에서는 누구나 보고 기여할 수 있게 합니다.

## 1. 대상 조직과 현황

### 대상: 학과 내 학기 프로젝트 팀들 (약 10개 팀, 팀당 3~4명)

| 현황 | 문제 |
|------|------|
| 팀마다 GitHub 저장소를 따로 만들고 **비공개**로 운영 | 다른 팀이 같은 기능(로그인, CI, 배포)을 처음부터 다시 만듦 |
| CI/CD, DORA 지표 수집 같은 공통 작업을 팀마다 따로 구현 | 품질 편차가 크고 학기마다 같은 시행착오 반복 |
| 졸업하면 저장소가 방치됨 | 4학년 프로젝트의 상당수가 이어지지 못하고 사라짐 |
| 팀 간 교류는 오프라인 질문에 의존 | 지식이 사람에게만 남고 기록되지 않음 |

### 시범 프로젝트: RunCrew의 DORA 지표 수집 도구

이 저장소의 [`scripts/dora/`](../../scripts/dora/)와 [대시보드](../../dashboard/)를 **학과 공용 컴포넌트**로 만드는 것부터 시작합니다.

**선정 이유**

- 모든 팀이 과제로 DORA 지표를 수집해야 해서 **수요가 확실함**
- 테스트(커버리지 99%)·CI·ADR·기여 가이드가 이미 갖춰져 있어 **바로 기여받을 수 있는 상태**
- 앱 도메인과 무관한 도구라 팀 간 이해관계 충돌이 적음

## 2. 기대 이점과 도전 과제

| 이점 | 설명 |
|------|------|
| 중복 제거 | CI·지표 수집을 팀마다 만들지 않고 공용 도구를 재사용 |
| 품질 향상 | 여러 팀이 리뷰하고 버그를 찾아 고치므로 혼자 만든 것보다 견고 |
| 지식 공유 | 이슈·PR·ADR에 결정 이유가 남아 다음 학기 학생도 이어받음 |
| 협업 역량 | 다른 팀 코드를 리뷰하고 기여하는 경험 (실무 오픈소스 기여 연습) |

| 도전 과제 | 해결 방안 |
|-----------|-----------|
| "우리 팀 코드를 보여주기 싫다" (평가·표절 우려) | 공용 컴포넌트만 공개, 앱 코드는 팀 저장소에 유지. 기여는 PR 기록으로 남아 **기여도 증빙**이 됨 |
| 다른 팀 PR을 리뷰할 시간이 없음 | 리뷰를 과제 점수(PR 리뷰 3건)와 연결, SLA 추적 자동화로 리뷰 지연을 보이게 함 |
| 누가 유지보수할지 불분명 | **Trusted Committer**(관리 책임자)를 학기마다 지정, CODEOWNERS로 명시 |
| 기여 방법을 모름 | CONTRIBUTING, `good first issue` 라벨, 리뷰 가이드 제공 |

## 3. 단계별 로드맵

```
1단계 문화 (2주)  →  2단계 도구 (2주)  →  3단계 파일럿 (4주)  →  4단계 확산 (다음 학기)
```

### 1단계: 문화 (1~2주차)

| 할 일 | 산출물 |
|-------|--------|
| Inner Source 설명회: 왜 하는지, 무엇을 공개하는지 합의 | 발표 자료, 합의 사항 기록 |
| 공개 범위 원칙: "공용 컴포넌트는 학과 전체 공개, 앱 코드는 팀 비공개" | 원칙 문서 |
| Trusted Committer 2명 지정 (현재 관리자 + 다른 팀 1명) | CODEOWNERS 갱신 |
| 비난 없는 리뷰 문화 안내 | [리뷰 가이드](../REVIEW_GUIDE.md), [행동 강령](../../CODE_OF_CONDUCT.md) |

### 2단계: 도구 (3~4주차)

| 할 일 | 산출물 |
|-------|--------|
| 학과 GitHub Organization에 공용 저장소 이전, 학과 구성원에게 **internal** 공개 | `dora-toolkit` 저장소 |
| 다른 저장소에서 쓰기 쉽게 **Reusable Workflow**로 배포 | `uses: org/dora-toolkit/.github/workflows/collect.yml@v1` |
| `good first issue` 5개 이상 등록 | 이슈 목록 |
| Discussions에 Q&A, RFC 카테고리 운영 | 질문·제안 창구 |

### 3단계: 파일럿 (5~8주차)

| 할 일 | 산출물 |
|-------|--------|
| 2~3개 팀이 공용 도구를 자기 저장소에 적용 | 적용 저장소 목록 |
| 적용하면서 생긴 문제를 **이슈와 PR로 기여** | 외부 팀 PR |
| 격주 회고: 무엇이 기여를 막았는지 정리 | 회고 기록, 개선 이슈 |
| `v1.x` 릴리스와 릴리스 노트 | GitHub Releases |

### 4단계: 확산 (다음 학기)

| 할 일 | 산출물 |
|-------|--------|
| 파일럿 결과를 바탕으로 전 팀 적용 | 적용률 보고 |
| 두 번째 공용 컴포넌트 후보 선정 (예: 로그인, 공통 UI) | RFC Discussion |
| Trusted Committer를 다음 학기 학생에게 인계 | 인계 문서 |

## 4. 성과 지표 (KPI)

| 영역 | 지표 | 측정 방법 | 파일럿 목표 (8주차) |
|------|------|-----------|---------------------|
| 참여도 | 외부 팀 기여자 수 | PR 작성자 중 다른 팀 구성원 수 | **5명 이상** |
| 참여도 | 외부 팀 PR 비율 | 머지된 PR 중 다른 팀 PR 비율 | **30% 이상** |
| 재사용 | 공용 도구 적용 팀 수 | 적용 저장소 수 | **3개 팀 이상** |
| 재사용 | 코드 재사용률 | 적용 팀에서 직접 작성하지 않고 공용 도구로 대체한 CI·지표 코드 비율 | **70% 이상** |
| 협업 속도 | 첫 PR까지 걸린 시간 | 새 기여자의 첫 방문(이슈 등록) → 첫 PR 머지 | **7일 이내** |
| 협업 속도 | PR 리뷰 대기 시간 | PR 생성 → 첫 리뷰 (SLA 추적 워크플로우) | **24시간 이내 90%** |
| 품질 | DORA 4대 지표 변화 | 공용 저장소의 [DORA 대시보드](https://hc1ab.github.io/example_RunCrew/) | 변경 실패율 **15% 이하** 유지 |

### 측정 자동화

- PR 리뷰 대기 시간: [SLA Tracker](../../.github/workflows/sla-tracker.yml)
- 기여자·PR 수: [Weekly Summary](../../.github/workflows/weekly-summary.yml) 이슈에 외부 기여자 항목 추가 예정
- DORA 지표: [DORA Metrics](../../.github/workflows/dora-metrics.yml)

## 5. 위험과 대응

| 위험 | 신호 | 대응 |
|------|------|------|
| 기여가 한 팀에만 몰림 | 외부 PR 비율이 2주 연속 10% 미만 | `good first issue` 추가, 과제 연계 강화 |
| 리뷰 병목 | SLA 초과 PR이 3개 이상 | Trusted Committer 추가 지정 |
| 공용 도구 변경으로 다른 팀 CI가 깨짐 | 적용 팀의 CI 실패 | SemVer로 버전 고정(`@v1`), 호환이 깨지는 변경은 메이저 버전으로 |
