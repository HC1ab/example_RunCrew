# ADR-0005: npm 다운로드 캐시 대신 node_modules를 캐시한다

- **상태**: 승인됨
- **날짜**: 2026-11-14
- **결정자**: @HC1ab
- **관련**: 이슈 #32, PR #33, [CI 최적화 리포트](../ci-optimization-report.md)

## 배경

CI의 모든 job이 의존성 설치(`npm ci`)를 반복합니다. `actions/setup-node`의 `cache: npm`이 일반적인 권장 설정이라 처음에는 이를 적용했지만, 효과를 실제로 측정해 보기로 했습니다.

## 검토한 선택지 (각 3회 실측, 전체 파이프라인 기준)

| 선택지 | 동작 | 설치 단계 합계 | Windows 설치/job |
|--------|------|---------------:|-----------------:|
| A. 캐시 없음 | 매번 레지스트리에서 `npm ci` | 61.3초 (기준) | 10.9초 |
| B. `cache: npm` | `~/.npm` 복원 후 `npm ci` | 75.0초 (**+22.3%**) | 12.1초 |
| C. **`node_modules` 캐시** | 적중 시 `npm ci` 생략 | 57.3초 (**−6.5%**) | 8.4초 (**−22.9%**) |

## 결정

> **C. `node_modules`를 OS·Node 버전·`package-lock.json` 해시를 키로 캐시하고, 적중하면 `npm ci`를 건너뛴다.**

의존성이 80개뿐이라 B는 "캐시 복원 비용 > 다운로드 비용"이 되어 오히려 느려졌습니다. C는 설치 자체를 생략하므로 특히 파일 쓰기가 느린 Windows에서 효과가 컸습니다.

- 키에 OS와 Node 버전을 넣은 이유: 네이티브 모듈이 생기면 플랫폼별로 빌드 결과가 달라지기 때문
- 키에 lockfile 해시를 넣은 이유: 의존성이 바뀌면 자동으로 새로 설치
- 측정을 위해 수동 실행에서 `none` / `npm` / `node_modules`를 고를 수 있게 유지

## 결과

- 👍 설치 단계 −6.5%, Windows job −22.9%
- 👎 전체 Wall 시간 개선은 −3.2%로 작고, 러너 편차 범위 안에 있을 수 있음
- 👎 `node_modules` 캐시는 `npm ci`의 "깨끗한 설치" 보장을 일부 포기함 → lockfile 해시가 키에 있어 의존성 변경 시에는 항상 새로 설치
- 🔁 의존성이 크게 늘거나(예: 앱 테스트 도구 추가) 네이티브 모듈이 생기면 같은 방법으로 다시 측정
