# ADR-0001: 기술 결정을 ADR로 기록한다

- **상태**: 승인됨
- **날짜**: 2026-11-14
- **결정자**: @HC1ab
- **관련**: 이슈 #35

## 배경

프로젝트를 진행하면서 DORA 지표 정의, CI 구조, 머지 방식 같은 결정을 여러 번 내렸습니다. 그런데 결정의 이유는 PR 리뷰 코멘트나 커밋 메시지에 흩어져 있어서, 나중에 "왜 이렇게 했지?"를 찾으려면 여러 PR을 뒤져야 했습니다.

실제로 PR #33 리뷰에서 "선택적 배포로 Deployment Frequency 의미가 바뀌는데 어디에 기록할지"라는 질문이 나왔습니다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. PR·커밋 메시지에만 남김 | 추가 작업 없음 | 흩어져 있어 찾기 어려움, 결정의 전체 맥락이 없음 |
| B. Wiki에 기록 | 편집이 쉬움 | 코드와 버전이 따로 관리됨, 리뷰를 거치지 않음 |
| C. 저장소 `docs/adr/`에 ADR로 기록 | 코드와 함께 버전 관리, PR 리뷰를 거침, 형식이 일정함 | 작성 비용이 조금 듦 |

## 결정

> **C. 저장소의 `docs/adr/`에 Michael Nygard 형식의 ADR로 기록한다.**

결정은 코드와 같은 PR에서 리뷰받아야 하고, 코드가 바뀌면 결정 기록도 함께 바뀌어야 하기 때문입니다.

- 파일 이름: `NNNN-결정-요약.md` (번호는 순서대로, 재사용하지 않음)
- 형식: [template.md](template.md)
- 결정을 바꿀 때는 기존 ADR을 고치지 않고 **새 ADR을 만들고** 기존 ADR의 상태를 "ADR-XXXX로 대체됨"으로 바꿉니다.

## 결과

- 👍 PR 리뷰에서 "이건 ADR로 남기자"라고 요청할 수 있는 기준이 생김
- 👍 새로 합류한 사람이 결정의 이유를 한곳에서 확인 가능
- 👎 사소한 결정까지 ADR로 남기면 부담이 됨 → **되돌리기 어렵거나 지표·구조에 영향을 주는 결정**만 기록
