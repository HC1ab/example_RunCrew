# ADR-0002: GitHub Deployments와 incident 라벨을 DORA 지표의 데이터 출처로 쓴다

- **상태**: 승인됨
- **날짜**: 2026-11-14 (실제 결정: 2026-10-15)
- **결정자**: @HC1ab
- **관련**: 이슈 #18, PR #19, #22

## 배경

DORA 4대 지표(배포 빈도, 리드 타임, 변경 실패율, 복구 시간)를 GitHub Actions로 자동 수집해야 했습니다. 지표를 계산하려면 **언제 배포됐는지**와 **언제 장애가 났다가 복구됐는지**를 기록할 곳이 필요했습니다.

외부 모니터링 서비스나 DB는 비용과 설정 부담이 있어 학기 프로젝트 범위에 맞지 않았습니다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. main 머지(PR merged)를 배포로 간주 | 구현이 가장 쉬움 | 실제 배포 성공/실패를 알 수 없어 변경 실패율 계산 불가 |
| B. Release·태그를 배포로 간주 | 버전 단위로 명확 | 학기 중 릴리스가 드물어 배포 빈도가 의미 없어짐 |
| C. **GitHub Deployments** (Pages 배포 시 자동 생성) | 배포마다 성공/실패 상태와 커밋 SHA가 남음, 추가 비용 없음 | Pages 배포에 묶임 |
| 장애 기록: 외부 모니터링 | 실제 장애 자동 감지 | 비용, 설정 부담 |
| 장애 기록: **`incident` 라벨 이슈** | 이슈 생성~종료로 복구 시간 측정 가능, 사람이 판단 | 사람이 직접 등록해야 함 |

## 결정

> **배포는 C(GitHub Deployments, `github-pages` 환경), 장애는 `incident` 라벨 이슈로 기록한다.**

- `actions/deploy-pages`가 배포마다 Deployment와 상태(success/failure)를 자동으로 남기므로 추가 코드 없이 데이터가 쌓입니다.
- 리드 타임은 직전 성공 배포와 이번 배포 사이의 커밋을 Compare API로 구해 계산합니다.
- 지표 갱신용 봇 커밋(`chore(metrics):`)은 리드 타임에서 제외합니다 (incident #21, PR #27 리뷰).

## 결과

- 👍 별도 인프라 없이 GitHub API만으로 4대 지표를 모두 계산
- 👍 incident #21에서 실제 MTTR(9분) 측정까지 검증됨
- 👎 incident는 사람이 등록해야 해서 누락될 수 있음 → 기여 가이드에 `incident` 라벨 기준을 명시
- 🔁 앱(Flutter)을 실제로 배포하게 되면 앱 배포 환경의 Deployment도 수집 대상에 추가
