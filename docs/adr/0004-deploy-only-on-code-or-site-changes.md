# ADR-0004: 코드나 대시보드가 바뀐 경우에만 배포한다

- **상태**: 승인됨
- **날짜**: 2026-11-14
- **결정자**: @HC1ab
- **관련**: 이슈 #32, PR #33 (리뷰 [QUESTION]), PR #34, [CI 최적화 리포트](../ci-optimization-report.md)

## 배경

처음 CI/CD(PR #31)는 main에 push될 때마다 Lint → Test(9개 조합) → Build → Deploy를 모두 실행했습니다. 그래서 README 오타 수정 같은 **문서 변경에도 테스트 9개와 배포가 실행**됐습니다.

이 방식은 두 가지 문제가 있었습니다.

1. 러너 시간 낭비: PR 한 번에 job 11개, 약 189초
2. DORA 배포 빈도 왜곡: 내용이 같은 사이트를 다시 배포해도 "배포 1회"로 집계

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. 항상 전체 실행·배포 | 단순, 누락 없음 | 러너 낭비, 배포 빈도가 실제보다 높게 측정 |
| B. 워크플로우 `paths` 필터로 아예 실행 안 함 | 설정이 간단 | 필수 체크가 "대기 중"으로 남아 브랜치 보호와 충돌 |
| C. **job 단위 변경 감지** (`paths-filter`) + 결과 집계 job | 필요한 job만 실행, 필수 체크는 항상 결과가 남음 | 워크플로우가 조금 복잡해짐 |

## 결정

> **C. 변경 파일을 `code` / `site`로 분류해 job 단위로 실행 여부를 정하고, main에서는 코드나 대시보드가 바뀐 경우에만 배포한다.**

- `code` (scripts, test, package, 워크플로우) → Lint, Test, Build, Deploy
- `site` (dashboard) → Build, Deploy
- 둘 다 아님 (문서 등) → 모두 생략, `CI Result`만 통과

DORA의 Deployment Frequency는 **"변경이 프로덕션에 반영된 횟수"** 를 재는 지표이므로, 내용이 같은 재배포를 세지 않는 것이 정의에 더 가깝다고 판단했습니다.

## 결과

- 👍 문서 전용 PR: job 11개 → 2개, job 시간 189초 → 8초 (−95.8%)
- 👍 배포 빈도가 실제 변경 배포만 반영
- 👎 이 결정 이후 배포 빈도가 이전보다 낮게 나옴 → **지표 하락은 측정 기준 변경 때문**이며 이 ADR로 설명
- 👎 분류 목록에 새 경로를 빠뜨리면 그 변경은 테스트·배포가 안 됨 → 새 최상위 폴더를 만들 때 `ci.yml`의 필터를 함께 수정 (리뷰 체크리스트)
- 🔁 앱 코드가 추가되면 `app` 분류를 새로 만든다
